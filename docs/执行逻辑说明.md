> 本文档梳理 E:\ai\AI-Chat 全部功能的执行逻辑,按"入口 → 主流程 → 子系统"组织。
> 代码入口:`app.py`(Flask + Waitress),Agent 核心:`agent/orchestrator.py`。
> 最后核对时间:2026-08-09(基于 2026-08-05 之后的代码状态)。

## 一、总体架构与启动流程

### 1.1 技术栈与模块布局

- Flask(页面 + JSON API)+ Waitress(WSGI,默认 4 workers)+ SQLite(WAL 模式)
- Agent 为自研 ReAct 循环(非 LangChain):`agent/orchestrator.py` 驱动,LLM 走 OpenAI 兼容接口(`agent/llm_client.py`),多后端(DeepSeek / Xiaomi MIMO / OpenAI / Gemini / Claude)
- 数据:SQLite `data/chat.db`(users / conversations / messages / memories / approval_requests / conversation_summaries / scheduled_tasks / scheduled_task_runs + memories_fts 全文索引)
- 配置:`data/config.yaml`(API key 用 `${ENV}` 占位符,真实 key 存 .env)

### 1.2 启动顺序(app.py main())

```
解析 -H/-p/--workers → 注册 SIGINT/SIGTERM 优雅停机
  ├─ _start_auto_backup()    :30 秒后首次备份,之后每 24h 循环(run_backup,保留 30 份)
  ├─ _start_scheduler()      :AgentScheduler.start(),启动定时主动任务
  ├─ alert_engine.start()    :告警引擎,每 60s 健康检查
  └─ waitress.serve(...)     :正式对外服务(无 waitress 回退 Flask dev server)
```

模块加载期(import 时)完成:日志三文件(TimedRotating 午夜轮转 30 天)、Metrics、AlertEngine、dotenv、load_config、LLMClient、AgentLLMClient、create_agent、TraceStore、ApprovalManager、MountManager、cancellation_manager、TaskStore + AgentScheduler。

### 1.3 配置加载与保存

- **加载** `load_config()`:读 config.yaml → `_resolve_env_api_keys()` 把 `${DEEPSEEK_API_KEY}` 类占位符解析为 os.environ 中的真实 key,并记录 `api_key_env` 标记;未设置环境变量则告警日志。
- **保存** `save_config()`:深拷贝(JSON round-trip)→ `_restore_env_api_keys()`(key 仍是 env 当前值则还原为占位符)→ 写 tmp 再 `os.replace` 原子替换(Windows Defender 锁文件时 5 次重试)。
- **生效路径**:`_get_active_backend()` 优先级 = `active_backend` 指定 → 第一个 enabled backend → 第一个 backend;改配置后通过 `agent_llm.update_config(config)` 实时生效。
- **新 key 录入**:POST /api/config/backend 时明文 key 自动写入 .env(git 忽略),config.yaml 只存占位符;GET /api/config 对 key 一律掩码(占位符型显示 `${ENV}`,明文型只露前 8 + 后 4)。

## 二、认证与请求管线(所有功能的前置)

### 2.1 认证(auth.py)

1. 登录 POST /login:先查 IP 限流(5 次/300s 滑动窗口,超限 429 锁定 300s)→ `authenticate()`(用户名格式 + `check_password_hash`)→ 成功则 `session.clear()`(防会话固定)+ 写 `session["user"]`。
2. 所有页面/API 挂 `login_required`:无 session 则存 `next` 并重定向 /login。
3. 密码:werkzeug 盐值哈希存 SQLite users 表;仅 admin 用户。

### 2.2 CSRF 防护

`before_request` 钩子:除 GET/HEAD/OPTIONS、/login、/logout、/static 外,所有写请求必须带 `X-CSRF-Token` 头或 JSON `_csrf_token`(session 生成的 32 字节 hex,`hmac.compare_digest` 比对),失败 403。响应统一加安全头(CSP、X-Frame-Options、nosniff)。

### 2.3 限流(两层,各自独立)

| 层 | 位置 | 规则 |
|---|---|---|
| 登录限流 | auth.py RateLimiter(内存) | 每 IP 5 次/300s,锁 300s |
| Agent 工具限流 | agent/security/rate_limiter.py(全局单例,与定时任务共享) | 每用户 30 次/分钟、200 次/小时;全局 100 次/分钟;token 预算 50 万/小时;并发槽位 5 个 |

工具限流作用于 agent 每次工具调用前(`check_tool_call` / `acquire_concurrent`),HTTP 层除登录外无限流。

## 三、聊天主流程(/api/chat 与 /api/agent/stream)

### 3.1 /api/chat(同步,current_agent.run())

```
请求进入(login_required)
  ├─ 校验:空消息+空附件 → 400;消息 >10000 字符 → 400
  ├─ 会话:有 conv_id 则 load;否则新建(12 位 hex,标题=消息前 40 字)
  ├─ 附件处理(最多 8 个,两遍):
  │    ① 构建描述文本 attach_lines:mount→目录清单;图片→[图片]名;文本→内联前 10000 字节;其他→路径描述
  │    ② 构建结构化 image_parts:mount/image(带 data URL)/text/doc 分类
  │    合并为 effective_message = 附件块 + 用户消息
  ├─ 视觉检测:有图片且 agent_llm.supports_vision=False → 短路:
  │    消息+附件照常入库,直接返回"当前大模型不支持多模态…" + vision_blocked:true,不调 LLM
  ├─ 按当前登录用户重建 agent(current_agent):挂 trace_sink / approval_manager / cancellation_manager
  ├─ current_agent.run(message, conversation_id, run_id, user_attachments=image_parts)
  ├─ 收尾:消息 ≤2 条时标题改为消息前 40 字;update_conversation
  └─ 返回 {conversation_id, content, title, cancelled}
```

### 3.2 /api/agent/stream(SSE 流式,模块级 agent.run_stream)

流程与同步版一致,差异:

- 图片不支持视觉时仍带 kind="image" 元数据(无 data URL),描述行统一 `[图片] 名`
- 视觉短路改为 SSE 流内 yield 一条 text 事件(带 vision_blocked 语义)
- `generate()` 逐条转发 run_stream 事件:`{"type": "plan"|"tool_call"|"tool_result"|"text"|"done"|"error"|"cancelled"}`,SSE 头禁缓冲
- 异常 yield error 事件;finally 里更新标题、会话、消息统计
- 注意:流式接口用模块级 `agent`(username="admin"),同步接口用当前用户专属 agent

### 3.3 /api/chat 内部消息构建(_build_initial_messages)

1. system prompt(替换 `{current_date_time}`)
2. **长期记忆注入**:`memory_service.build_injection_context(query, max_memories=4, min_importance=2)` → `[长期记忆]` system 块(命中记忆刷新 last_accessed_at)
3. DB 历史(`get_messages_for_llm`,限 20 条)
4. 用户消息(多模态图片附件 → `[{type:text},{type:image_url}]` content 数组)
5. 持久化摘要注入:有 conversation_summaries 记录 → `[对话摘要]` system 块
6. `context.fit_messages()` 按 token 裁剪到 32000 窗口(保留最近 4 条)

## 四、Agent 核心循环(agent/orchestrator.py)

### 4.1 run() / run_stream() 外层

1. `_reset_approval_memory()`:清空本次运行审批记忆
2. 前置检查:`validate_message()` → `check_tool_call()` 限流 → `acquire_concurrent()` 并发槽
3. try/finally 调 `_run_loop()`(或 `_run_stream_loop()`),finally 释放槽位 + `cancellation_manager.clear(run_id)`

### 4.2 主循环每轮迭代

```
① 计划注入:iteration==0 且应规划 → PlanGenerator.generate() 生成 [计划] system 块插入 messages[1]
             iteration>0 → 用 [计划进度] n/m 块替换旧进度块
② 守卫检查(每轮开头):取消? → 工具预算超限? → 运行超时(600s)?
③ 压缩检查:iteration>0 时 _maybe_compress_messages()(见 §10)
④ LLM 调用:llm.chat(messages, tools=全部 schema);记录 native/prompt 模式
⑤ 响应分派:
    - 纯文本 → 持久化消息 + 记忆抽取(_maybe_extract_memories),正常结束(text_response)
    - tool_use → 逐个执行工具,结果按模式回填:
         native:追加 role:"tool" 消息
         prompt:格式化 XML 块追加为 role:"user" 消息
⑥ 循环守卫记账(identical-call / failure-loop,见 §4.4)
⑦ continue 下一轮
```

结束判定(三种自然结束 + 兜底):LLM 返回纯文本;响应无有效工具调用;迭代耗尽(999 次 → iteration_limit)。流式版每步以事件 yield,有独立 `stream_tool_calls` 预算,但**没有** identical-call / failure-loop 守卫。

### 4.3 工具执行 _execute_tool 完整流水线

```
1  工具查找:tools.get(name),未知名 → "Unknown tool" + 可用列表
2  审批检查(_check_approval,仅 write_file/execute_code/memory_forget/delegate):
    - 无 manager → fail-safe 直接拒绝
    - 审批记忆命中(本次运行内已决策) → 批准则静默通过,拒绝则直接返回拒绝结果
    - 否则创建 pending 请求,阻塞轮询(1s 间隔,超时 300s 自动过期)等用户决策
3  挂载审批注入:文件工具带 _approval_cb 时注入 _current_run_id("allow" 策略按运行记忆)
4  权限检查:permissions.can_use_tool(username, tool)(类别 × 用户等级)
5  限流检查:check_tool_call() → 超限返回 rate_limited 失败(不计入 failure-loop 守卫)
6  参数规范化(write_file):解多层 {"arguments": "..."} 包裹;paths/files/file_path/filename 别名 → path
7  输入校验:validator.validate_tool_args(参数超限/注入模式 → 拒绝并附格式提示)
8  重试执行循环:
    - 成功 → record_tool_call() 记账,返回(附 duration)
    - 失败:rate_limited(60s 窗口内不恢复)与 approval(人工决定)不重试;
      其余瞬态错误(网络/超时/5xx)+ 工具 retryable → 指数退避重试(最多 2 次)
    - 重试历史写入结果 metadata,LLM 可见
```

### 4.4 循环守卫与预算(同步版)

| 守卫 | 触发 | 阈值 | 行为 |
|---|---|---|---|
| identical-call | 连续相同 `tool:json(args)` 调用 | 写工具 12;其他 6;空参 write_file 6;上次结果 rate_limited 则清零 | 返回 loop_detected 失败 |
| failure-loop | 连续失败次数 | ≥8(rate_limited 不计入,且每次触发 1s 退避) | 返回 failure_loop + 最近错误摘要 |
| 预算 | tool_calls_made | ≥300(delegate 按 mode 扣 quota:research=1/code=2/full=3) | 返回 tool_limit |
| 超时 | elapsed | >600s(config 可调) | 返回 timeout |
| 取消 | should_stop(run_id) | DIRECT 即停 / CONFIRM 批准才停 | 返回 cancelled |
| 迭代兜底 | max_iterations | 999 | 返回 iteration_limit |

另有工具结果去重缓存(同参数成功结果复用;delegate 永不缓存)。

### 4.5 工具清单

| 工具 | 功能 | 权限类别 | 可重试 |
|---|---|---|---|
| read_file | 读单文件(FileGuard 五层防护) | READ | ✓ |
| read_files | 批量读(≤15 文件,每文件 ≤400 行) | READ | ✓ |
| write_file | 写文件(自动建目录;空参时从响应文本恢复参数) | WRITE | ✗ |
| list_files | 列目录(≤100 项,支持 glob) | READ | ✓ |
| execute_code | 沙箱执行 Python(30s 超时,受限 import) | EXECUTE | ✗ |
| web_search | Tavily 优先 / Bing 兜底(15s 超时) | NETWORK | ✓ |
| get_weather | wttr.in 天气 + 3 日预报(支持中文城市) | READ | ✓ |
| chat_completion | 循环内嵌套 LLM 调用(推理/总结) | SYSTEM | ✗ |
| memory_query | FTS5 + BM25 语义搜索记忆 | READ | ✓ |
| memory_store | 显式存记忆(去重检测) | WRITE | ✗ |
| memory_forget | 按 id 删记忆(需审批) | WRITE | ✗ |
| memory_list | 列最近记忆(≤50 条) | READ | ✓ |
| delegate | 派生子代理(需审批) | SYSTEM | ✗ |
| `<server>__<tool>` | MCP 服务器工具适配(权限按服务器配置) | 按配置 | ✗ |

权限模型:ADMIN=全部;USER=READ+WRITE+EXECUTE+NETWORK+SYSTEM;GUEST=仅 READ。判定顺序:全局 deny → 用户级 deny → 类别默认 → 显式 allow → 默认拒绝。

## 五、长期记忆(agent/memory/)

### 5.1 四个执行时机

1. **注入(每轮对话前)**:按用户消息搜索 FTS5(分段器 CJK bigram 分词,BM25 排序),取最多 4 条 importance≥2 的记忆拼成 `[长期记忆]` system 块;命中则刷新访问时间。
2. **自动抽取(每轮对话后)**:预过滤(用户消息 ≥8 字符 + 助手回复 ≥8 字符)→ 非阻塞锁(每用户)→ 单次 LLM 调用(temperature=0.1,输出严格 JSON)→ 质量门过滤(AI 自我描述、"你好"类寒暄、长度 4~500)→ store_many。全程 fail-soft。
3. **合并(抽取后)**:同类型两两比较 token 重叠率(≥0.8 且交集 ≥3)→ 低重要度并入高重要度(importance 相加封顶 5)。
4. **衰减(定时/维护)**:30 天未访问 → importance-1(下限 1);90 天未访问且 importance<4 → 删除(重要记忆永不自动删)。

### 5.2 去重与冲突解决(database.store_memory)

| 情况 | 判定 | 处理 |
|---|---|---|
| 7 天内同类型同内容 | 重复 | 刷新时间,importance+1(封顶 5) |
| 180 天内同类型不同内容 | 事实变更(如"住上海"→"搬北京") | 新 claim importance 更高 → 替换旧记忆;否则保留 |
| 跨类型 | 不冲突 | 各自存储 |

显式工具:memory_query / memory_store / memory_list / memory_forget(用户隔离)。API:/api/agent/memories 全套。

## 六、Plan-then-Execute 规划(agent/planning/planner.py)

### 6.1 触发条件

用户消息 ≥30 字符,或含动作 cue 词(写/创建/分析/搜索/生成/代码/报告等)。规划失败(fail-soft)自动退化为普通 ReAct,不阻塞聊天。

### 6.2 执行流程

```
生成:单次 LLM 调用(temperature=0.2, max_tokens=1200)输出 JSON {goal, steps[≤8]}
      解析容错:剥 markdown fence → 提取最外层 {} → 截断 JSON 修复(补引号/补尾部)
跟踪:每个工具调用后 note_tool() 启发式匹配步骤
      (工具名命中步骤描述;read_file→"读取/查看",write_file→"写入/保存/创建",
       execute_code→"代码/运行",搜索类→"搜索/查询" 等)
注入:每轮以 [计划进度] n/m 块注入上下文,模型知道当前位置
复查:每 plan_review_every(3) 次工具调用后,StepReviewer 把步骤状态 + 最近 12 次
      工具调用快照发给 LLM(temperature=0),可补标记 completed 或取消标记
      (纠正启发式误判);每轮最多 4 次复查,失败保留启发式进度
```

配置:planning.enabled / min_user_chars / review_enabled / review_every / review_max_calls。

## 七、人类审批(agent/approval/manager.py)

### 7.1 触发

仅对副作用工具(write_file / execute_code / memory_forget / delegate)在**执行前**检查。`approval_enabled` 默认 false(opt-in),app.py 从 config 显式开启。

### 7.2 流程

```
执行工具前 → ApprovalStore 插入 approval_requests(pending, expires_at=+300s)
  → wait_for_decision 阻塞轮询(1s 间隔,超时自动标记 expired)
  → 用户批准 → 继续执行;拒绝/过期 → 返回带 metadata["approval"] 的失败结果
    (人工决定,永不自动重试)
```

### 7.3 审批记忆(approval_remember)

- 本次运行内(每次 run/run_stream 开始 `_reset_approval_memory`)按工具记录决策:
  - 已批准 → 后续同工具静默放行,不再弹窗
  - 已拒绝 → 直接返回"用户之前已拒绝"结果,不再询问
- 记忆按工具隔离(批准 write_file 不自动批准 execute_code);trace 记录命中事件。

API:GET /api/approvals、POST /api/approvals/<id>/approve|reject(CSRF 保护)。前端右下角审批卡片堆栈,3s 轮询。

## 八、定时主动任务(agent/scheduler.py)

### 8.1 调度

- APScheduler BackgroundScheduler,时区 Asia/Shanghai,5 字段 cron 表达式(分 时 日 月 周)
- 每任务 `max_instances=1`(重叠跳过)+ `coalesce=True`(错过的合并执行一次)
- 格式非法 → 跳过该任务并告警;apscheduler 未安装 → 仅禁用不崩溃

### 8.2 执行与并发控制

```
到点触发 → 共享 RateLimiter.acquire_concurrent()(与实时聊天共用 5 个槽位)
  ├─ 槽位被占 → 标记 SKIPPED 记录历史,不排队(绝不阻塞聊天)
  └─ 有槽位 → agent_factory() 创建全新 agent 实例(独立 workspace)
        → 执行 prompt → 结果写入任务绑定的 conversation_id(聊天里可见)
        → 记录 SUCCESS/FAILED + duration + trace_id
```

### 8.3 成功判定

从 trace 的 `finish_reason == "text_response"` 判断成功(run() 返回值无法区分守卫失败);无 trace 时退化为有 content 即成功;失败取最后一个 error 事件。

API:页面 /scheduled + /api/scheduled/tasks CRUD + <id>/run 手动触发 + /api/scheduled/runs 历史(15s 自动刷新,带 trace 回放链接)。

## 九、取消对话(agent/cancellation.py)

### 9.1 状态机与模式

```
CancellationRequest: NONE → PENDING → APPROVED / DENIED(过期按 DENIED)
DIRECT(聊天模式):PENDING 即停 — 循环每轮开头检查,立即优雅中止
CONFIRM(任务模式):PENDING 不停,仅 APPROVED 才停;DENIED/超时(120s)→ 继续执行
```

### 9.2 前后端协作

- 任务模式判定:后端 `_is_task_mode_message`(≥30 字或动作词);前端 `isTaskMode` 同逻辑
- 前端:聊天模式点取消 → 直接 POST direct;任务模式 → confirm() 弹窗,批准走 approve、拒绝走 deny
- 响应带 `cancelled: true` 时前端提示"已停止生成";FINISH_REASONS 新增 "cancelled"
- 因当前是同步 POST + 轮询(非 SSE),run_id 由前端生成传入,循环在每轮迭代开头 `_cancel_requested()` 检查

API:POST /api/cancel(run_id + mode)、/api/cancel/<run_id>/approve|deny、GET /api/cancel/<run_id>。

## 十、上下文压缩(agent/compression/)

### 10.1 触发条件(全部满足)

1. 压缩可用且 enabled,iteration > 0(首轮不压缩)
2. 消息数 ≥ min_messages(10)
3. token 总量 ≥ budget × trigger_ratio(32000 × 0.75 = 24000)
4. 收益 ≥ min_gain_tokens(800)——摘要成本约 0.3k token,必须真省钱才压缩

### 10.2 压缩动作

```
分离 system 块(系统提示/记忆/计划 → 永不压缩)
→ _find_boundary 从后往前找最近的完整工具往返边界
  (assistant tool_calls + 其 tool 结果成对保留,最近 keep_recent=6 条保留原文)
→ 旧消息渲染为 用户:/助手:/工具: 文本,单次 LLM 调用增量合并摘要
  (已有摘要截前 8000 字符作为基础;目标 320 字/硬顶 900 字;
   摘要太短/失败 → 降级纯截断,绝不中断对话)
→ 组装为 [对话摘要] system 消息 + 保留的近期消息
→ sanitize_tool_roundtrips 清理截断缝产生的孤立 tool 消息(防 API 400)
→ save_summary 持久化到 conversation_summaries 表(下次回合起始注入)
```

### 10.3 双保险

- orchestrator 每次 LLM 调用前跑 `_maybe_compress_messages`,重组结果统一过 `sanitize_tool_roundtrips`
- 压缩后仍超预算 → `_truncate_to_budget` 只整体丢弃"工具往返组",保证 assistant(tool_calls)+ tool 结果永远成对

## 十一、子代理 delegate(agent/tools/delegate.py)

### 11.1 模式与工具划分

| 模式 | 工具集 |
|---|---|
| research | 只读集:memory_query/memory_list/list_files/read_file/read_files/web_search/get_weather/chat_completion |
| code | research + write_file + execute_code |

### 11.2 执行

```
父代理调用 delegate(task, mode)
→ 子代理 = 新建 AgentOrchestrator(共享 db/llm/memory_service,独立 trace recorder)
   预算:工具 ≤25 次、时长 = min(父剩余, 300s);planning/compression 关;
   记忆抽取关(不污染长期记忆);共享父的权限/限流/校验实例
→ 同步阻塞执行;父按 mode 扣 quota(research=1/code=2/full=3)
→ 结果:subagent_id/content/tool_calls/finish_reason/trace_id;
   finish_reason 非 text_response/no_valid_tool_calls → 视为失败
→ 父 trace 记录 subagent 事件卡片(链接子 trace)
```

## 十二、MCP 服务器(agent/mcp/manager.py)

### 12.1 连接生命周期

```
config.yaml mcp_servers 段 → 每服务器独立 asyncio event loop 线程("mcp-loop")
  → _connect_once():stdio_client(命令+参数+env)或 streamable_http_client(url)
    (SDK 2.0 snake_case 与旧版 camelCase 兼容)
  → ClientSession.initialize() → list_tools()
  → 连接成功:回调把工具包装成 MCPTool 注册进 ToolRegistry

  → 断线:每 2s 探测,异常后 5s 重试,累计约 5 分钟放弃(error 状态)
```

### 12.2 调用与监控

- 调用经 `call_tool()`(60s 超时),结果归一化 {success, output, is_error},与内置工具一样走权限/trace/守卫流水线,`retryable=False`
- API:/api/mcp/servers(状态)、/api/mcp/tools、/api/mcp/reload(热重载,需 confirmed:true)
- Monitor 弹窗显示服务器卡片(状态点、工具 chips、错误)与 Reload 按钮
- mcp 包缺失 → 仅 MCP 相关路径报错,应用其余功能正常

## 十三、挂载目录(agent/mount/manager.py)

### 13.1 挂载与校验

- 持久化 data/mounts.json(原子写):{id(12 位 hex), name, path, policy, created_at}
- `validate_path`:绝对路径、存在且为目录、黑名单拒绝(/etc、/var、/usr、C:\Windows 等)

### 13.2 访问控制

- **policy = always_ask**:每次访问都走人工审批(文件工具带 `_approval_cb` 注入运行 id)

- manifest() 生成目录清单(≤200 条),挂载 id 兼作聊天附件 file_id
- API:/api/mounts 全套(列/挂/改策略/卸/清单)

## 十四、代码沙箱(agent/security/sandbox.py)

用户代码写入临时 .py,由自动生成的 wrapper 脚本在**子进程**(`subprocess.run([sys.executable, wrapper])`)中执行,而非主进程 exec:

```
① 静态预扫描:禁 import、eval/exec、../ 路径穿越 → security_warnings
② 运行时劫持 builtins.__import__:拦截 subprocess/socket/requests/pickle/importlib/
   os.system 等 20+ 危险模块(报错信息提示安全替代:open()/os.path/math/json/re)
③ 运行时守卫:os.remove/unlink/rmdir/system/chmod/rename 等破坏性操作
   仅允许作用于 agent 自己的 workspace 内(注入 __WORK_DIR__),否则 PermissionError
④ 资源限制:30s 超时、输出截断 100KB、UTF-8 + errors=replace(Windows GBK 兼容)
⑤ 干净环境:仅 PATH/HOME/TEMP 等,清空 PYTHONPATH
⑥ 执行后删除 wrapper 与用户代码两个临时文件(防泄漏)
```

ALWAYS_ALLOWED 白名单:math/json/re/datetime/csv/hashlib 等安全模块。

## 十五、文件读写防护(file_guard.py + validator.py)

**FileGuard.validate_path 五层检查**:① 路径穿越(resolve 后必须在允许目录内)→ ② 敏感路径黑名单(/etc/passwd、/proc、C:\Windows\System32 等)→ ③ 文件类型黑名单(.exe/.dll/.so/.sqlite/.bat/.sh/.ps1 等)→ ④ 符号链接解析后目标仍在允许目录内 → ⑤ 读写均 1MB 上限。另含 sanitize_filename、validate_content_size。

**InputValidator**:消息 ≤10000 字符;工具参数 JSON ≤50000;代码 ≤50000;正则黑名单拦截 prompt 注入("ignore all previous instructions" 等)与危险代码模式(os.system/subprocess/eval/exec/__import__);文件参数错误信息会反馈 LLM 提示正确格式。

## 十六、文件上传与多模态

### 16.1 上传(/api/upload)

- multipart 字段 `file`,可带 `conv_id`;限制 20MB,空文件/超限拒绝
- 存储:带 conv_id → `data/uploads/<conv_id>/<file_id><ext>`;不带 → 平铺目录;历史遗留文件 → `data/uploads/_legacy/`(O(1) 路径拼接,绝不遍历)
- 返回 {file_id, name, size, mime, kind(image/text/doc), url};GET /api/uploads/<path> 预览(防路径穿越,支持会话目录/平铺/_legacy)

### 16.2 发送链路

```
前端附件 chip(≤8 个,图片缩略图)→ 随 message 提交 attachments: [{file_id, name, conv_id}]
→ api_chat/api_agent_stream 构建附件元数据
→ 视觉能力检测(agent_llm.supports_vision):
    ✓ 支持 → 图片转 base64 data URL,user_attachments 传 OpenAI 多模态 content 数组
    ✗ 不支持 → 短路:不调 LLM,直接返回/流式输出"当前大模型不支持多模态…"
      (vision_blocked:true;用户消息仍持久化)
→ 附件元数据持久化到 messages.attachments JSON 列(历史消息可还原缩略图)
```

supports_vision 判定:backend 显式 `supports_vision` 优先,否则按模型名关键字白名单(vision/gpt-4o/claude-3/gemini/qwen-vl/mimo 等);LLM 调用收到 404/400 且错误含 image/multimodal not support → 兜底转友好提示。

### 16.3 会话文件列表

GET /api/conversations/<id> 响应带 `files`(该会话上传文件夹按时间倒序,≤100);前端 convFiles 面板展示(图片缩略图,点击新窗口);kind=="mount" 的附件在会话记录中过滤(挂载非会话文件)。

## 十七、可观测性 trace(agent/observability/)

### 17.1 记录

一次 agent 运行 = 一条 trace(12 位 hex,含 username/conversation_id/backend/model)。orchestrator 挂 recorder 后上报:

- LLM 调用(消息摘要取最后 40 条、响应截 4000 字符、token 统计)
- 工具调用 + 结果(参数递归脱敏:api_key/token/secret/password → ***)
- 计划生成/进度/复查、记忆注入/抽取、压缩事件、安全事件(权限拒绝/校验失败/限流)、循环守卫、子代理事件
- finish():15 种结束原因(text_response/tool_limit/iteration_limit/loop_detected/rate_limited/cancelled 等)+ success + 时长

### 17.2 存储与回放

- 每 trace 一个 JSON 文件 data/traces/(原子写),内存索引;超 500 条按最旧裁剪
- 页面 /traces:列表(成功过滤)+ 详情时间线回放(LLM prompt 折叠、工具链、token 统计、结束原因),10s 自动刷新,可删除
- 所有 report 方法 fail-soft,观测永不打断 agent 循环

## 附:A 常见问题排查速查

- **"disk I/O error"**:主机应用持有 WAL 锁,用 `file:chat.db?mode=ro&immutable=1` 只读验证主库健康;需停应用后删 chat.db-wal/-shm
- **API 400 tool 消息配对断裂**:检查压缩/截断路径 — sanitize_tool_roundtrips 应已兜底
- **工具被拒(权限)**:新工具必须加入 TOOL_CATEGORIES 与相应默认权限
- **写配置前先备份对比**:设置保存路径可能污染 config.yaml(曾有 mimo 配置被改事件)
- **跑测试**:`python3 -m pytest`(pytest.ini 已配 pythonpath);test_app/test_upload 需重定向临时 DB,清理逻辑绑定 "ai-chat-app-test-" 前缀,绝不碰生产库
